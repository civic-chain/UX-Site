# Client Feedback Cycle

Правила работы с фидбэком клиента и темпом итерации. Подгружай этот файл когда обсуждаешь с пользователем что сказал клиент, планируешь отправку, готовишь скриншоты для клиента, или планируешь работу под клиентский deadline.

## Цели

- Темп клиентского фидбэка — 1-2 недели.
- Стандарт качества — ship-it-fast: скорость итерации важнее идеальных пикселей.
- **Приоритет №1 — отдать клиенту красивые лендинг-страницы** на их утверждённой копии и базовой структуре (Justin canonical), но с нашей улучшенной дизайн-системой и явными дизайнерскими сокращениями слабых секций. Формат сдачи лендингов — ссылка на `*.vercel.app` preview. Дизайнерский продукт, не код.
- **Приоритет №2 — передача кодовой базы клиенту в красивом виде**, годной для их LLM-агента (если они будут использовать). Важно, но второстепенно. Структурная санитария Stage 4 — это инструмент для дизайнера, чтобы было легче доводить визуал до красоты, а не главная цель.

## Контекст Клиентской Работы

- Пользователь — дизайнер. Клиент — CivicChain (маркетинг + директор).
- Этот репо — V2 мастерская: клиент взял наш V1 код, сделал свою live-версию (`_docs/Civic-Chain-Justin/`), переписал текст. Мы итерируем visual поверх их утверждённой копии и структуры.
- Этот репо — внутренняя песочница для клиентского ревью, не публичный сайт.
- Цикл: дизайнер пушит итерацию → main мгновенно публикуется на `*.vercel.app` → клиент может реагировать в любой момент → дизайнер итерирует.
- Свой домен не нужен; `*.vercel.app` хватает.

## Две Сдачи

- **Stage 6 — сдача визуального продукта клиенту.** Формат: ссылка на `*.vercel.app` preview. Acceptance: лендинги визуально красивые, дизайн-система применена согласованно, копия не уехала от Justin canonical, структурные отклонения только по явному решению пользователя. Никакого кода, никакого LLM-handoff чек-листа на этой стадии — это дизайнерский deliverable.
- **Stage 7 — передача кодовой базы для LLM-агента.** Формат: уточняется с клиентом ближе к стадии (push в их репо / архив / другое). Acceptance: AGENTS.md / criteria / README / `_docs/design-system.md` синхронизированы с реальным кодом, cold-LLM probe пройден на выбранной клиентом форме их агента (или на свежей Claude-сессии как proxy если форма ещё не известна).
- После явного user approval визуала оставшаяся работа до preview — cleanup и verification, не новый редизайн. Визуальный цикл открывать заново только по новому решению пользователя.

## Handoff Legibility — Когда Применяется

- Phase-boundary cold-LLM probe (между Stage 4 и Stage 5) был пройден при закрытии Phase 03 — структурный фундамент проверен.
- Continuous gate на каждый push отменён: context-switch между «делать визуал» и «верифицировать handoff» съедает фокус и темп.
- **Stage 5 (визуальная итерация) handoff'а не требует** — ship лендингов на vercel и есть смысл стадии. AGENTS.md и `_docs/design-system.md` обновляются по факту, если итерация поменяла shape: это гигиена, не gate.
- **Stage 7 (передача кодовой базы) — финальный handoff pass.** Полный cold-LLM walkthrough, sweep AGENTS.md / criteria / README / design-system.md на свежесть и stale-ссылки. Это там, где проверяется, что чужой агент справится с репо.
- **Stage 7 package boundary.** Отдаём код + агентный слой (`AGENTS.md`, `CLAUDE.md`, `.codex/`, нелокальные `.claude/`, `.mcp.json`) + README / `_ops` / `_docs/design-system.md`; не отдаём корневые scratch PNG, `_docs/landing-page/**` и локальные сборочные папки.

## Sign-off Перед Push

- Перед каждым push'ем итерации в `main` — critic-pass через `Smith` (trajectory critic) или `brooks` (structural critic) поверх diff'а / live-результата. Smith — для проверки, что задача не дрейфует от стратегии и acceptance criteria; brooks — для structural review кода / shape репо. Выбор зависит от природы итерации.
- Push в main = публикация на `*.vercel.app`; клиент видит сразу. Significant визуальный артефакт без critic-pass'а — недопустим.
- Для visual review, особенно с субагентами, давать не только full-page скриншоты, а короткие focused captures конкретных секций, кнопок и проблемных блоков. Так critique видит реальный объект разбора, а не теряется в длинной странице.

## Аудитория И Цель Landing'а

- Аудитория landing'а: town managers / мэры маленьких городов США + партнёры/советники/пресса.
- Стадия CivicChain: идея + whitepaper. Продукта в проде нет.
- Цель landing'а для посетителя: запросить demo/pilot. CTA сейчас декоративный.

## Каналы Фидбэка

- Текст в чате/email, скриншоты с разметкой, голос на встречах.
- Письменный фидбэк по Landing 01 живёт у дизайнера в локальной папке «комментарии» **вне репо**. При работе над правкой — спрашивать у пользователя релевантную часть, не искать в репозитории.
- Секциям landing'а нужны стабильные id-якоря (`#hero`, `#portal-hub`) — клиент пишет «в #hero поменяй X».
